# D-DBA-40: `sql_tuning_advisor` writes the script that tunes one sql id and reads stored findings; it never creates a task
**Status:** Accepted
**Date:** 2026-11-14
**Issue:** DBA-40
**Confluence:** none (plan doc on claude.ai, section "Check catalogue", row "SQL tuning"; design in epic DBA-23)

**Decision:** `sql_tuning_advisor` is a mode A check (`pack: tuning`, `params: sql_id:sql_id`, `max_rows` 60) run as the advisory user through `python -m tools advise`. Its script rows are a PL/SQL block that calls `DBMS_SQLTUNE.CREATE_TUNING_TASK(sql_id => '<id>', task_name => 'STA_<id>_<YYMMDDHH24MISS>')` and `EXECUTE_TUNING_TASK`, ends with a `/` line, then `SELECT DBMS_SQLTUNE.REPORT_TUNING_TASK('<task>') FROM dual;`. Its fact rows, after the script, are the findings and recommendations already stored for SQL Tuning Advisor tasks whose `SQL` object has `ATTR1` = the sql id (`DBA_ADVISOR_OBJECTS`, `_TASKS`, `_FINDINGS`, `_RECOMMENDATIONS`): task, recommendation type (the finding's type when it has none), benefit in percent and message cut to 200, `WARNING` at 30% or more. A fact row's `SCRIPT_LINE` is a `-- ` comment, so the written file lists the stored findings below the script. The check itself creates, executes and drops nothing.

**Why:** Measured 2026-11-14 on Oracle 23ai Free 23.26.3, FREEPDB1, as `dba_agent_adv` (details in `tests/integration/checks/test_sql_tuning_advisor.py`'s docstring):
- (a) The expected `ORA-14551` did not happen. `SELECT dbms_sqltune.create_tuning_task(sql_id => ...) FROM dual` created a task and `SELECT dbms_sqltune.execute_tuning_task(...) FROM dual` executed it. So a single `SELECT` can change the advisor repository, and keeping the advisor out of the check is a rule of this pack, not something the database enforces. The integration tests count `DBA_ADVISOR_TASKS` before and after every check run.
- (b) For a task SYS created, `adv` reads `DBA_ADVISOR_TASKS`, `DBA_ADVISOR_OBJECTS` (one `SQL` row, `ATTR1` the sql id), `DBA_ADVISOR_FINDINGS` and `DBA_ADVISOR_RECOMMENDATIONS`. `BENEFIT` is hundredths of a percent (the report prints 9647 as 96.47%). `REPORT_TUNING_TASK` of another user's task needs `owner_name` (`ORA-13605` without it), so the script reports only the task it just created as the same user. `SYS_AUTO_SQL_TUNING_TASK` does not exist in Free (`pending.md`).

The task name carries the time it was written because `CREATE_TUNING_TASK` refuses a name that already exists: a fixed `STA_<id>` would make every second run of the script fail, and dropping the old task first would delete the findings this check reports. `STA_` plus 13 plus `_` plus 12 characters is exactly 30, the shortest identifier limit among supported versions.

**Rejected:** Running the advisor from the check (a `SELECT` calling `CREATE_TUNING_TASK`): it works, but a check must change nothing (D-DBA-36-mode-a-script-contract), and a PL/SQL block is more than one statement (lint L009). Running it through the read-only user: user decision 2026-11-13; that user must stay unable to start advisor tasks (D-DBA-5-read-only-grants). Granting `ADMINISTER SQL TUNING SET` or `ADMINISTER ANY SQL TUNING SET` to the advisory user: not needed to read stored findings, and D-DBA-26-advisory-tier-grants allows a new grant only after measuring the error it removes. A fixed task name with a drop-first step in the script: deletes earlier findings and adds a destructive line for no gain.

**Impact:** The check creates no advisor task: its SQL calls no `DBMS_SQLTUNE` or `DBMS_ADVISOR` function, and any change that adds one fails the before-and-after `DBA_ADVISOR_TASKS` counts in `test_sql_tuning_advisor.py`. Skills run it only through `advise` (`tuning.md`, `advisory.md`). Script rows come before fact rows so `FETCH FIRST 60` can cut only stored findings, never the script. Script rows have a NULL `TASK_NAME`; fact rows name their task.
