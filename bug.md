# Bugs

- 2026-11-12, found in DBA-21 /implement (windows-latest probe, PR #18, run 43198647960): `check-test` with `SQLCL_BIN=<sqlcl>\bin\sql` fails on Windows with `[WinError 193] %1 is not a valid Win32 application`. SQLcl 25.3.2's `bin/` holds the shell script `sql` beside `sql.exe`, and `CreateProcess` starts the script when it exists. `SQLCL_BIN=<sqlcl>\bin\sql.exe` and a bare `sql` on PATH work. Fixed in DBA-21: `tools.sqlcl.launcher` swaps in the `.exe` beside it.
- 2026-11-12, found in DBA-21 /implement (CI runs 43198643726 and 43200907912, branch DBA-21 merged with DBA-8 and `main` at `ee08e50`): `tests/integration/checks/test_sessions.py::test_idle_transaction_then_blocking_tree_scenario` (DBA-12) fails in both SQLcl 25.3.2 integration cells (Java 17 and 21) of both runs with `McpTimeout: no reply to tools/call within 30.0s`; the `latest` cells pass. Not caused by DBA-21. Cause ([DBA-22](https://aavisangle.atlassian.net/browse/DBA-22)): `run_sql(asynchronous=True)` sent `executionType="ASYNCHRONOUS"` to `run-sql` whenever it was offered, but 25.3.2's `run-sql` declares only `model` and `sql` (25.4.2 adds a separate `run-sql-async` instead), so SQLcl ignored the argument and ran the scenario's blocked `update` synchronously until the client timed out. Fixed in DBA-22: the asynchronous form is sent only when the run tool's input schema declares an execution type argument, otherwise `AsynchronousUnsupported` is raised with nothing sent, and the scenario runs that update on a background thread (`docs/decisions/D-DBA-22-asynchronous-run-sql-from-tool-schema.md`).
- 2026-11-12, found in DBA-19 /tdd-prep, corrected in DBA-20: when a query fails during a later fetch, SQLcl's `run-sql` returns the rows fetched before the failure with a normal row-count footer and no `ORA-` in the tool result. Probe (comment on DBA-19; SQLcl 26.3.1.301.1413, Oracle 23.26.3 Free, as SYSTEM): `select to_number(decode(level, N, 'x', '1')) n from dual connect by level <= M` failing at row 3 of 5 returns an error report with `ORA-01722` and no rows; at row 25 of 26, 10 rows and `10 rows selected.`; at row 26 of 26 and 26 of 60, 25 rows and `25 rows selected.`; at row 51 of 60, 40 rows and `40 rows selected.`. The `ORA-01722` text is written to the MCP server's stdout outside any JSON-RPC message; `tools/mcp_client.py` skips non-JSON lines, so `SqlResult.error` is None and the result looks complete. The same query through `sql -S` returns the error report. Inferred from these points, not established: a first fetch of 10 rows and later fetches of 15. Not tested: other error types, SQLcl 26.1, other MCP clients, a non-SYSTEM user. Not fixable in `find_error`: the error is not in the tool result. Accepted for v1.0, not detected: `docs/decisions/D-DBA-20-accept-truncated-result-on-fetch-error.md`; user-facing note in `README.md` (Known limitations).
- 2026-11-12, found in DBA-19 /review: `parse_csv` drops a NULL row of a one-column numeric result. SQLcl 26.3 prints a NULL number as an empty field, so `select cast(null as number) n from dual union all select 1 from dual` returns `'"N"\n\n1\n\n'`; `parse_csv` filters empty records and returns `rows == [['1']]`, one row short. Predates DBA-19. Fixed in DBA-20: in a one-column result an empty line is a NULL row `['']`, except the blank line SQLcl writes after the last record.
- 2026-11-12, found in DBA-15 /implement: SQLcl 26.3.1 starts `sql -home <dir> -mcp` below restrict level 3 when no `-R` is given. Through `sqlcl_run`, `@doctor_probe.sql` returns `SP2-0310: Unable to open file` (it tried) and `host echo x` runs the OS command; with `-R 3` or `-R 4` both return `SP2-0738`. The spike (26.1) saw `SP2-0738` at the default. `SqlclSession` starts SQLcl with no `-R` (DBA-4), and D-DBA-2 and D-DBA-3 assume the default is level 4, so on 26.3.1 the pack's sessions can run host commands. Doctor's `restrict-level` check FAILs on it. Fixed in DBA-15: the pack always passes `-R 4` (D-DBA-15-sqlcl-explicit-restrict-level-4).
- 2026-11-12, found in DBA-6 /implement: `parse_csv` (`tools/sqlcl_text.py`) misses the row-count footer when the count has a thousands separator. `_FOOTER` matches `\d+ rows? selected\.`, so `1,718 rows selected.` is returned as a data row `['1', '718 rows selected. ']`. Any result of 1,000 rows or more gains a bogus last row. Through DBA-7's runner, a check returning 1,000 rows or more got the bogus row: an `IndexError` in `validate_result` (a traceback from `check-test`) or a false max_rows and severity report. Fixed by `/integrate 3` (third pass): `_FOOTER` accepts a count with commas, and the workaround in `tests/support/make_awr_fixture.py` is gone.
- 2026-11-12, found in DBA-6 /implement: through `sql -mcp` (SQLcl 26.3) an `UPDATE` or `INSERT` applies (`2 rows updated.`) but the result also carries `ORA-17273: Could not commit with auto-commit enabled.`, so `SqlResult.error` is set for a statement that succeeded. DDL and queries are unaffected. Cause: the MCP connection runs with auto-commit on (`docs/decisions/D-DBA-12-manual-commit-through-saved-url.md`).
- 2026-11-12, found in DBA-20 /review (same on `main` before DBA-20): `find_error` returns None for two real SQLcl 26.3.1 error texts from `run_sql` on the test container, so `SqlResult.error` is None. (1) A PL/SQL block that fails to compile, `begin\n"X";\nend;`, returns `'"X";\n *\nERROR at line 2:\nORA-06550: line 2, column 2:\n...'` with no `Error starting at line` preamble; `_layout` takes `"X";` for a CSV header and the block runs to the blank line, hiding `ORA-06550`. (2) An unknown command returns `Error report -\nUnknown Command` with no `ORA-` or `SP2-` code.
- 2026-11-11, found in DBA-12 /review: `rollback` through SQLcl MCP (26.3.1, ordinary user, connection saved with `?oracle.jdbc.autoCommit=false`) replies `Rollback complete.` and the change is committed; any next call on the session commits it. Not fixable in the pack. Detail: `docs/decisions/D-DBA-12-manual-commit-through-saved-url.md`. Cause found 2026-11-13 (orchestrator probe, SQLcl 26.3.1.301.1413, Oracle 23.26.3 Free, `-R 4`): the missing `DBTOOLS$MCP_LOG` table in the connected user's schema. With that table pre-created in each user's schema (DDL copied from the one SQLcl creates for SYSTEM), an ordinary user with or without `CREATE TABLE` behaves like SYSTEM: an `update` stays uncommitted through a later `select`, and `rollback` undoes it, proven by a `create table` after the rollback (its implicit commit left both updated rows unchanged). SQLcl wrote its log rows into each user's table. Not yet tested: how a held change is committed on purpose (`commit` is `Unknown Command`), SQLcl 25.3.2 and 25.4.2, and whether the table needs exactly SYSTEM's DDL. This reopens the write-tier design; see the D-DBA-12 record.
- 2026-11-13, seen by /integrate 3 (fourth pass) from the code, not run on Windows: under Python 3.10/3.11 on Windows, doctor's `java` check reports `java not found` when `JAVA_HOME` is set, and its `sqlcl` check fails with WinError 193 when `SQLCL_BIN` names `<sqlcl>\bin\sql`. `RealEnv.run` (`tools/doctor/env.py`) resolved `$JAVA_HOME/bin/java` and `bin\sql` with `shutil.which`, which before 3.12 does not try `PATHEXT` for a path with a directory part. Unit tests use `FakeEnv`, so CI never reached `RealEnv.run`. Fixed by /integrate 3: `RealEnv.run` starts programs through `tools.sqlcl.launcher()`.
- 2026-11-13, found in DBA-31 /tdd-prep (probe on the test container, 23.26.3): `segment_growth` filters `dba_hist_snapshot.begin_interval_time >= SYSTIMESTAMP - INTERVAL '7' DAY`. `begin_interval_time` is a TIMESTAMP without time zone in the database host's clock, so Oracle reads it in the SQLcl session's time zone, which SQLcl takes from the client (Asia/Kolkata on the dev machine, UTC on GitHub runners). The 7-day window moves by the client's offset from the database host (5.5 hours here). Measured on ASH: with the session at +09:00, the same predicate on `v$active_session_history.sample_time` over 15 minutes counted 0 rows; `CAST(SYSTIMESTAMP AS TIMESTAMP)` counted 41. CI cannot see it because runner and container are both UTC.
- 2026-11-13, found in DBA-45 /review (PR #43): with `_hosts` now before `known.sub`, a known name holding `$` or `#` (or `-` before an IPv4) ahead of a host-shaped tail leaks its prefix: connection `prod#erp.acme.com` reads `prod#<host>`, `erp$svc.acme.com` reads `erp$<host>` (before DBA-45: `<connection-1>`). `_FQDN_RE` and `_IPV4_RE` lookbehinds stop at fewer characters than `Known.sub`'s `(?<![\w$#-])`. The host stays hidden. Not fixed.
