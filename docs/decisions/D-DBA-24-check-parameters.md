# D-DBA-24: Checks take typed parameters through a `params` header and `{{name}}` placeholders, filled by one binder
**Status:** Accepted
**Date:** 2026-11-13
**Issue:** DBA-24
**Confluence:** none (plan doc on claude.ai, section "Customising checks and reports"; design in epic DBA-23)

**Decision:** A check is one file `plugin/checks/<category>/<id>.sql`: a header of `-- key: value` lines with a fixed key set (`id`, `title`, `category`, `mode`, `min_version`, `max_rows`, `pack`, `remediation`, optional `max_version`, optional `params`), then exactly one SQL statement. `params` is a comma-separated list of `name:type` or `name:type=default`, `name` matching `[a-z][a-z0-9_]*`. There are two types: `sql_id` (a value fully matches `[0-9a-z]{13}`, no default allowed) and `int` (a value fully matches `[0-9]{1,9}`, default required). The body writes a parameter as `{{name}}`, inside or outside a string literal. `tools.checks.params.bind(check, values)` is the only code that fills placeholders: it adds defaults, refuses a missing value, an unknown name or a value that fails its type's pattern with `ParamError`, and returns the `Check` with its SQL filled. `render_file(check, values)` fills the whole file the same way; `python -m tools check-sql` prints it for the model to send unchanged, and `check-test --param` binds before running. The statement must alias a column `AS severity` whose literal values are limited to `CRITICAL`, `WARNING`, `OK`, `INFO`, and must end with `FETCH FIRST <max_rows> ROWS`. `python -m tools lint` enforces this as codes L001 to L017: L015 a malformed `params` list, L016 a `{{` in the body that names no declared parameter, L017 a declared parameter the body never uses. L016 and L017 are judged only when `params` is well formed. Supersedes D-DBA-3-check-header-format, whose rules are carried forward here except its reservation of `params`.

**Why:** The model sends a check unchanged through SQLcl's `run-sql` at restrict level 4 (D-DBA-15-sqlcl-explicit-restrict-level-4), where output is always CSV and SQL*Plus commands are refused (`spike/RESULTS.md`). A computed `severity` column makes the result itself the verdict, and the `FETCH FIRST` cap bounds output size in the database rather than in the client. Several Epic B checks need a value per run (a `sql_id`, a number of minutes, snapshot ids), and SQLcl offers no safe way to pass one: `&name` through `run-sql` returns "Substitution cancelled" with no error (`_setup_sql_statements` in `tests/integration/conftest.py`), and `run-sql` takes no bind variables. So the pack fills the text itself, and a value can only reach the SQL after a full match against a pattern that admits no quote, space, sign or newline. Both types are needed by the planned checks and neither can carry SQL.

**Rejected:** `&` substitution: cancelled silently through `run-sql`. Bind variables: `run-sql` has none. A free-text or string type: any SQL could be passed in. The model filling placeholders itself: the text sent would be untested and unvalidated; `check-sql` gives it the filled file instead. An `int` without a default: the per-check harness and scheduled reports have no value to supply. From D-DBA-3: free-form headers (cannot be linted); thresholds in a separate config file (the plan doc keeps thresholds in the check's SQL so `run-sql` output is a verdict without a second lookup).

**Impact:** Every file under `plugin/checks/` must pass `python -m tools lint`. A new header key, parameter type or lint code needs a lint change in the same PR; the next free code is L018. No code outside `tools/checks/params.py` fills a check's `{{name}}` placeholders (the tier templates' `{{user}}` and `{{profile}}`, filled by `setup-sql`, are not check parameters), and any code that runs or prints a parameterised check binds it first through `bind` or `render_file` (the harness binds `int` parameters to their defaults and `sql_id` parameters to a probe id). Body rules scan SQL with string literals, quoted identifiers and comments blanked out; `&` is flagged everywhere except inside string literals, comments included, because SQL*Plus-style substitution also applies there. Placeholder rules read the unmasked body, since `bind` fills placeholders wherever they appear.
